1 Portfolio Report Style Guide

1.1 Purpose

This is a cross-project writing guide for portfolio reports built in Quarto. It sets the prose strategy for the standard pages used across these projects. The goal is consistency of voice and quality, not uniformity of tone — each page serves a different audience and should read differently.

The two reference projects are:

  • veteran-lung-cancer-coxph — survival analysis using a built-in R dataset
  • nhanes-sdoh-bp-mlr — multiple linear regression on NHANES survey data

1.2 The Standard Pages

Each portfolio project uses some or all of these pages:

  • Index — project framing and navigation (always present)
  • Overview — findings-first summary for a general technical audience (always present)
  • EDA — exploratory analysis for a statistically literate audience (present when the project requires meaningful data wrangling or exploration; not required for well-understood built-in datasets)
  • Report — full analytical workflow for someone evaluating technical depth (always present)
  • Guide — self-reference and methods refresher (always present)

1.3 Units of Writing

Different pages use different primary units of composition. Write to the unit appropriate for the page, not to generic paragraphs.

Page Unit Structure
Overview Finding Headline → Support
EDA Analysis chunk Observation → Interpretation → Implication
Report Decision block Justification → Method → Result → Interpretation
Guide Workflow step Code → Rationale → Expected output or check

Page-specific rules define the unit. The unit defines the prose. When a unit structure is defined for a page, write to it — do not default to generic paragraph structure.

1.4 Global Writing Principles

These apply to every page.

  • Lead with the practical point before the statistical detail.
  • State findings precisely: “+4.9 mmHg”, not “somewhat higher”.
  • Each analytical step must include one sentence explaining why it is necessary for the model or interpretation.
  • Caveat responsibly: enough to be honest, not so much that the work reads as uncertain.
  • Write like one person throughout, even though each page targets a different audience.

1.4.1 Avoid across all pages

  • “In this section, we will…” — state what you are doing, do not announce it.
  • Textbook definitions unless they directly support an analytical decision.
  • Passive voice in interpretation paragraphs.
  • Overclaiming: “the results show” is fine; “this proves” is not.
  • Academic posturing: “it was observed that”, “these findings suggest that further research is warranted”, “consistent with the extant literature”.

1.5 Rule Precedence

Page-specific writing rules override global writing principles. When a page defines its own structure or verbosity constraints, follow those instead of the defaults.

Example: The EDA page requires one short analytical paragraph after each code chunk. This overrides the default paragraph length guideline.

1.6 Default Verbosity Constraint

Default paragraph length: 2–5 sentences. Avoid paragraphs longer than 5 sentences unless the page-level unit requires it.

Where a page defines its own verbosity rule (e.g. EDA), that rule takes precedence.

1.7 Page 1: Index

1.7.1 Audience

Anyone landing on the project for the first time.

1.7.2 Job To Do

Orient the reader: what the project is, what data it uses, what method it applies, and how the pages are organised.

1.7.3 Tone

Short, factual, neutral. A table of contents with a one-paragraph introduction. No findings, no interpretation. Let the pages speak.

1.7.4 Writing Rules

  • One paragraph introduction: dataset → method → question. Five sentences maximum.
  • Section descriptions are 2–3 lines: what the page covers, nothing more.
  • No claims, no findings, no personality.

1.7.5 Target Effect

The reader knows immediately what the project is about and where to go.

1.8 Page 2: Overview

1.8.1 Audience

Recruiters, hiring managers, and general technical readers who may skim rather than read. A non-specialist should be able to follow the key findings; a reader with a statistics background should see that the author understands what they are doing.

1.8.2 Job To Do

Communicate the main findings clearly and confidently without requiring domain expertise to follow. Show — without stating — that the author understands the subject and the method.

1.8.3 Tone

Accessible but not dumbed down. Plain English for the findings; technical terms used precisely when they appear, but not leaned on for credibility. Think: a confident analyst briefing a team that includes both domain experts and non-specialists.

1.8.4 Writing Rules

  • Open with the research question or applied problem, not with a description of the method.
  • Use a findings-first structure: key results stated up front, supporting visualisations and detail after.
  • Do not explain the method in detail. The reader who wants that goes to the Report.
  • When statistical terms appear (hazard ratio, adjusted effect, R²), use them correctly but follow with a plain-English translation. Do not let technical terms carry the interpretation alone.

1.8.5 Finding Structure

Each finding must follow this structure:

  • Headline: Plain-English statement of the result
  • Support: One sentence including effect size, comparison group, and — if necessary — one caveat

Example:

Higher BMI is associated with increased systolic blood pressure. Each 5-unit increase in BMI corresponds to a +4.9 mmHg increase (95% CI: 3.1–6.7), adjusted for age and sex.

1.8.6 Target Effect

A non-specialist comes away with a clear sense of what the project found. A specialist comes away thinking: “This person understands the domain and can communicate results to a mixed audience.”

Reference pages: notebooks/veteran-lung-cancer-overview.qmd, analysis/overview.qmd

1.9 Page 3: EDA

Present when the project requires meaningful data exploration or wrangling — complex derived variables, missingness, raw survey data. Not required for well-understood built-in datasets. The veteran lung cancer project used survival::veteran and skipped this page; the NHANES project required wrangling across multiple raw files and included it.

1.9.1 Audience

A technically literate reader — statistician, data scientist, or senior analyst — evaluating whether the author can handle data responsibly before modelling.

1.9.2 Job To Do

Show careful, methodical preparation: variable derivation, recodes, missingness, distributional checks, and unadjusted associations. Demonstrate that modelling decisions are grounded in the data.

1.9.3 Tone

Technical but readable. More analytical than the Overview, but not academic. A lab notebook a senior colleague could follow easily — not a methods section. Show work and reasoning, not erudition.

EDA prose should sound like a calm senior analyst walking a technical reader through the data: descriptive first, interpretive second, cautious about causality, and explicit about what must wait for adjusted modelling.

1.9.4 Writing Rules

  • Each section opens with one sentence stating why this step is necessary for the model or interpretation — not a description of what is about to be done.
  • After each code chunk, write one short analytical paragraph of 3–5 sentences. The paragraph should usually move from what the output shows, to what it means, to why it matters for modelling, but it should read naturally rather than mechanically.
  • Close the page with an EDA summary: what the data showed and what it implies for the modelling approach.
  • Avoid strong forward claims such as “will remain significant” unless the purpose is explicitly to preview a modelling question. Prefer restrained handoffs such as “may reflect confounding”, “will be estimated more precisely in the adjusted model”, or “is useful context for the regression notebook”.

1.9.5 Analysis Chunk Structure

After each code chunk, write one short analytical paragraph of 3–5 sentences. The paragraph should usually move from what the output shows, to what it means, to why it matters for modelling. These are rhetorical moves, not visible subheadings, and not every paragraph needs to distribute space across them in exactly the same way.

Do not format EDA commentary as bullet points, numbered items, or bolded labels like Observation. Interpretation. Implication. These are rhetorical moves, not visible headings.

The prose should name the visible pattern plainly, give a restrained technical reading of it, note any important inferential limit, and then hand off cleanly to the next modelling step where appropriate.

Each move is usually 1–2 sentences. The full paragraph should usually be 3–5 sentences maximum. This is the operative verbosity rule for this page and overrides the default paragraph length guideline.

Example paragraph:

Age and BMI show the clearest unadjusted gradients with the outcome, with prevalence rising steadily across older age groups and higher BMI categories. These are descriptive patterns rather than independent effects, since age, income, and BMI are related to one another in the sample. Even so, they identify the variables most likely to matter in the adjusted regression model and clarify where confounding is most likely to be important.

1.9.6 Target Effect

The reader should come away thinking: “This person knows how to handle messy data, understands the assumptions going into the model, and made defensible decisions.”

Reference page: analysis/eda.qmd

1.10 Page 4: Report

1.10.1 Audience

Someone evaluating whether the author can build, justify, and communicate a statistical workflow in a professional way.

1.10.2 Job To Do

Show analytical reasoning, model-building judgment, diagnostic discipline, and clear interpretation of results.

1.10.3 Tone

More formal than the Overview, but still readable and plain-spoken. This is not a journal submission — it is a professional demonstration of methodological competence. Precise and direct.

Report prose should sound like a capable analyst defending decisions in real time: plain-spoken, technically precise, and slightly more formal than the EDA, but never schematic or legalistic.

1.10.4 Writing Rules

  • Make the report skimmable: clear section openings, clear interpretations beneath each output, and a disciplined conclusion.
  • Caveats belong here: limitations, assumptions, what the analysis cannot tell us. State them once, clearly, and move on.
  • Keep textbook exposition out. A reader evaluating technical depth does not need to be taught basics — but does need to see that the author understands them.
  • Prefer short framing paragraphs before outputs and short interpretation paragraphs after outputs. The reasoning order should be clear, but it does not need to appear as a repeated labeled template.
  • Caveats should be specific and calmly stated. Avoid grand claims, defensive overqualification, or textbook exposition disguised as interpretation.

1.10.5 Decision Block Structure

Every section of analytical work should make four things clear:

  1. Justification — why this step is necessary: statistical validity, interpretability, or domain relevance
  2. Method — what was done
  3. Result — what the output shows
  4. Interpretation — what it means for the analysis

These are reasoning functions, not mandatory visible headings. The report should make them legible in the prose, but should not force them into a rigid surface template when a more natural paragraph structure is clearer.

Because justification comes first in the reasoning order, modelling decisions should be explained at the point they are made, not in retrospective summaries. Do not separate justification from the decision it explains.

Example flow:

  • A short framing paragraph explains why the next check, model, or comparison matters.
  • The code chunk shows what was done.
  • A short paragraph interprets the output and connects it to the next analytical step.

1.10.6 Target Effect

The reader should come away thinking: “This person knows how to run the analysis, defend the modelling choices, and explain the results responsibly.”

Reference pages: notebooks/veteran-lung-cancer-coxph-report.qmd, analysis/regression.qmd

1.11 Page 5: Guide

1.11.1 Audience

Primarily the author, returning to the method after a gap. Also other practitioners wanting a practical reference for the same type of analysis.

1.11.2 Job To Do

Act as a reusable working reference: package choices, workflow, syntax, key checks, and the statistical ideas worth retaining. Code and method decisions are the main event; prose supports them.

1.11.3 Tone

Practical and collegial. Written for a technically literate colleague — or for yourself six months from now. Not a beginner tutorial, not a formal report. Prioritises being useful over being polished.

1.11.4 Writing Rules

  • Open by explicitly stating this is a refresher and reference, not a portfolio summary.
  • Use collapsible callouts for theory so the main workflow stays uncluttered.
  • Do not include sections that add no practical value.

1.11.5 Guide Structure

The Guide should typically include these sections:

Section Status
Minimal working example Required
Key checks Required
Interpretation patterns Required
Common pitfalls Include when materially useful; omit if trivial

1.11.6 Workflow Step Structure

Each step within a section follows this unit:

  • Code — the minimal implementation step
  • Rationale — why this step is performed (decision or purpose)
  • Expected output or check — the specific signal that confirms correctness (e.g. model convergence, coefficient sign, diagnostic threshold, or visual pattern)

1.11.7 Target Effect

The reader (including the author) should come away thinking: “This is exactly the reference I would want if I knew the material once and needed to get back up to speed quickly.”

Reference pages: notebooks/veteran-lung-cancer-coxph.qmd, analysis/guide.qmd

1.12 Cross-Project Consistency

Each page serves a different audience, but all pages within a project must feel like the work of one person.

  • Use identical wording for the main outcome variable and key predictors across all pages.
  • Report effect sizes in the same units throughout — do not switch between scales across pages.
  • Do not reinterpret results differently between the Overview and the Report. The Overview simplifies; it does not contradict.
  • Maintain the same level of caution around inference across pages.
  • Same writing personality throughout: clear, capable, and grounded.

1.13 Editing Checklist

When revising a prose chunk, work through these questions:

  1. Do I know which page and audience I am writing for?
  2. Am I writing to the correct unit for this page?
  3. Is this paragraph doing useful work, or just sounding thorough?
  4. Can the point be made more directly?
  5. Is the statistical language still precise after simplifying it?
  6. Does every analytical step include one sentence explaining why it is necessary?
  7. Does this sound like the same author as the rest of the project?
